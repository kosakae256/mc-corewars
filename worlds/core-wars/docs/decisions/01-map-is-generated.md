# 決定: マップは手で建てず、コードで作る

2026-08-22 / **採用**（同日、下記のとおり範囲を修正）

## 決めたこと

**Core Wars のマップは、手作業で建築せず、コードで作る。**

> **修正（同日）:「毎回生成する」ではない。**
> マップの**デザインは固定**。一度コードで作り、`.mcstructure` に固めて使い回す。
> 生成器は**制作の道具**であって、実行時の仕組みではない。
> 詳細は [spec/08-map-authoring.md](../spec/08-map-authoring.md)。

マップの正体は「ブロックの並び」ではなく、
**`docs/spec/` に書かれた数値（島の大きさ・間隔・高さ・配置）**とする。
生成器がそれを読んでブロックを置く。

## なぜ

### 1. 完全対称が保証される

マップは 180 度回して重なる完全対称（[02-map.md](../02-map.md)）。
手で建てると、**片側を作って複製する**手間が要り、
複製し忘れやズレが必ず起きる。

生成器なら、対称は**計算で保証される**。ズレようがない。

### 2. 作り直しが安い（作っている間の話）

**このゲームは数値を詰める作業が大量に発生する。**

- 島が広すぎる／狭すぎる
- 橋の距離が長すぎる／短すぎる
- 拠点の中の配置が守りにくい

手で建てていると、これを試すたびに建て直しになる。
**生成器なら数値を変えて再生成するだけ。**
「試す」の費用が下がれば、それだけ詰められる。

### 3. ドキュメント駆動と噛み合う

手作業だと、**建てたものが正で、ドキュメントが後追い**になりやすい。
生成器なら**ドキュメントの数値が正**で、ワールドはその出力にすぎない。

`docs/spec/` を読めばマップが分かる、という状態を保てる。

### 4. 人手が無い

作り手がブロックを置かない前提。**そもそも手作業という選択肢が無い。**

## 捨てた案とその理由

| 案 | なぜ捨てたか |
| --- | --- |
| 手で建てて `.mcstructure` に保存 | 対称の担保と作り直しの費用が重い。人手も無い |
| 配布マップを持ってくる | ルールが自分たちの仕様と合わない。調整もできない |
| 一度だけ生成して、あとは手で微調整 | **ドキュメントとワールドがすぐズレる。** 生成器が信用できなくなる |

## この判断が崩れる条件

- **見た目にこだわりたくなったとき。**
  生成器で作れるのは規則的な形。凝った装飾は手作業の方が速い
- 生成器の実装が、マップ調整より重くなったとき
- 一度決まって、二度と変えないと確信できたとき

> そうなったら「生成した上に手で飾る」に移行してよい。
> ただし**その時点で、飾った分はドキュメントの管轄外になる**ことを受け入れる。

## 影響

- **`world/structures/` が本体になる。** 完成したマップはここに `.mcstructure` で置く
- **バックアップは引き続き要る。** ワールドには進行中の試合状態が入るため
- `kit` アドオンに**構造物を置く機能**を持たせる
- **下絵（プレビュー）ツールを先に作る。** 見ないまま作ると変なものができる
- マップの数値は `docs/spec/` と `kit` の設定に二重管理せず、**片方を正とする**
