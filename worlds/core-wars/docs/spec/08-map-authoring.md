# 仕様: マップの作り方

マップは**固定**。一度いいものを作って使い回す（[decisions/01](../decisions/01-map-is-generated.md) を後述のとおり修正）。
設計は [docs/game/02-map.md](../02-map.md)。

---

## 0. 一番の問題: 見ないまま作ると変なものができる

**作り手（Claude）はゲーム画面を見られない。**
座標を計算してブロックを置くことはできるが、
**それが「いいマップ」かどうかを自分で判断できない。**

このまま作れば、変なマップが量産される。当然そうなる。

**だから、見てから決める仕組みを先に作る。**

---

## 1. 作り方の方針

### 1-1. 3つの段階に分ける

| 段階 | やること | 見るもの |
| --- | --- | --- |
| **1. 設計** | 形・寸法・要素の配置を**文書と図**で決める | 文書 |
| **2. 下絵** | 設計をデータにして、**画像に描き出す** | **PNG（真上・斜め・断面）** |
| **3. 出力** | 納得したものだけを `.mcstructure` にする | ゲーム内 |

**段階2 が肝。** ゲームに入れる前に見る。
画像なら作り手も確認できるので、**明らかに変なものはここで止まる。**

### 1-2. なぜ 3D モデルからではないのか

MagicaVoxel などでモデルを作って取り込む道もあるが、採らない。

- **作り手が造形するなら、結局それは「手で作る」こと**。人手が無いという前提と矛盾する
- 変換の途中でブロックの種類が化ける。Minecraft のブロックは色数が限られる
- **修正が遅い。** モデルを直して再変換するより、数値を直して描き直す方が速い

**データ → 画像 → 構造物** の流れなら、直したいときに数値を1つ変えるだけで済む。

### 1-3. 何が作れて、何が作れないか

**正直なところ:**

| | 作れるか |
| --- | --- |
| 対称で整った競技場（幾何的なデザイン） | **作れる。** 得意 |
| 段差・柱・階段・縁取りなどの構造的な装飾 | **作れる** |
| 素材を使い分けた見た目の作り込み | **ある程度作れる** |
| 城・遺跡・street などのテーマ性のある造形 | **苦手。** 中途半端になる見込み |
| 有機的な地形（自然な岩肌、曲線の崖） | **苦手** |

**Core Wars は競技マップなので、幾何的で整った方が本来正しい。**
対戦ゲームのマップは、装飾より**読みやすさ**（どこに何があるか一目で分かること）が効く。

> **テーマ性のある見た目が欲しいなら、方式を変える必要がある。**
> その場合は正直に言う。作れないものを作れると言わない。

## 2. 下絵（プレビュー）

### 2-1. 何を出すか

`tools/mapview/` に置く Node のツール。設計データを読んで PNG を描く。

| 図 | 何が分かるか |
| --- | --- |
| **真上から** | 島の配置、大きさの釣り合い、橋の距離 |
| **斜めから** | 高低差、立体としての見え方 |
| **断面** | 厚み、段差の構成 |

**色はブロックの実際の色に寄せる。** 見た目の判断に使うため。

### 2-2. 使い方

```
設計データ（JSON / TS）
      ↓  tools/mapview
   PNG を出力
      ↓  見る（作り手も、あなたも）
   直す → 描き直す（安い）
      ↓  納得したら
   .mcstructure を出力
```

## 3. 構造物として持ち込む

### 3-1. 単位は「島ごと」

構造物ブロックの上限は **64 × 384 × 64**（公式ドキュメントで確認）。

| 島 | 一辺 | 収まるか |
| --- | --- | --- |
| 中央 | 81 | **収まらない → 4分割**（継ぎ目 27） |
| 拠点 | 41 | 収まる |

> 横の6島は [decisions/03](../decisions/03-three-islands.md) で無くした。

**マップ全体（約 144 × 128）は1つに収まらない。**
**島ごとに1つの構造物**にする。これは制約ではなく、むしろ都合がよい。

- 島を1つだけ差し替えられる
- 対称なので、**拠点の島は1つ作って両側に置ける**（180度回転）

### 3-2. 置き方

`@minecraft/server` の `StructureManager` が使える。

```
createFromWorld()   ワールドの範囲から構造物を作る
saveAs()            保存する
place()             置く
```

**手で構造物ブロックを操作する道もあるが、スクリプトから置く方が確実。**
座標を間違えないし、対称配置も計算で保証できる。

## 3-4. 構造物の配り方（2026-08-24 決定）

**構造物は `kit` アドオンに同梱する。**

```
worlds/core-wars/packs/kit/behavior_packs/kit/structures/corewars/*.mcstructure
                                        ~~~~~~~~
                                        これが名前空間になる
```

ゲーム内では:

```
/structure load corewars:mid_nw <x> <y> <z>
```

### なぜワールドフォルダに置かないか

ワールドの `structures/` に置く方式だと、**遊ぶワールドを変えるたびに配り直し**になる。
どのワールドで遊んでいるかを作り手が把握できないので、
「置いたはずなのに読めない」が起きる。実際に起きた。

パックに入れておけば、**有効にしたどのワールドでも読める**。
`leveler` が `leveler:empty` で先に実証していた方式。

### 名前空間はフォルダ名

`structures/<名前空間>/<名前>.mcstructure` → `<名前空間>:<名前>`

**`mystructure:` は、ゲーム内の構造物ブロックで保存したときの既定の名前空間。**
アドオンから配る場合は使わない。

### 落とし穴1: 名前でキャッシュされる（最重要）

**Minecraft は構造物を名前でキャッシュする。**
同じ名前のまま `.mcstructure` を差し替えても、**ゲームは古い中身を読み続ける。**
エラーは出ない。黙って古いものが出る。

これが一番たちが悪い。
「直したはずなのに変わらない」→「直し方が悪いのか」と実装を疑ってしまう。

**対策: 名前に版番号を付ける。**

```
mid_nw_v1  →（設計を直す）→  mid_nw_v2
```

`tools/mapview/publish.mjs` が自動でやる。
**中身のハッシュが変わったときだけ版を上げる**ので、
直していないのに番号が増えてコマンドが変わり続けることはない。
古い版のファイルは消す（残しても読まれないうえ、どれが最新か分からなくなる）。

版の記録は `world/structures/versions.json`。

> **人が「変えたつもり」かどうかで判定しない。** 必ず内容のハッシュで見る。

### 落とし穴2: ファイル名

`/structure load` は**ファイル名と完全に一致**していないと読めない。
1文字違うだけで、エラーではなく「無い」として扱われる。

> 実例: キャッシュを外すために `mid_nw.mcstructure` を `mid_nwa.mcstructure` に
> 改名したまま、読み込む側の名前を直し忘れて読めなくなった。
> **中央の島の北西が丸ごと欠け、その上の櫓が宙に浮いて見えた。**
> 構造物そのものは正常だった。

**読めないときは、まずファイル名を疑う。** 中身の破損より、名前の不一致の方がずっと多い。

### 落とし穴3: 継ぎ目に門を跨がせない

分割の継ぎ目を跨いだ構造は、**置く位置を1マス間違えるとそこだけ食い違う。**
壁のような一様な面なら気づきにくいが、**門だと一目でずれて見える。**

> 実例: 中央(41)で割っていたため、門(38..44)が真っ二つになっていた。

**継ぎ目は 27。** 門・天守・4つの櫓のどれも跨がない唯一の帯。

| 構造 | 範囲 |
| --- | --- |
| 門（四方） | 38..44 |
| 天守 | 28..54 |
| 隅櫓 | 6..20 / 62..76 |
| 壁 | 13..15 / 67..69 |

分割後の大きさは 27 と 55（上限 64 に収まる）。

**コマンドは絶対座標で出す。** 相対で出すと足し算を間違える。

### 中央の島は4分割

構造物の上限は 64 × 384 × 64。中央の島は 82 × 82 なので収まらない。
**北西・北東・南西・南東の4つ**に割る。並べる順は下記のとおり。

### 3-3. 奈落は既にある

**ワールド側で用意済み。** 生成器で地面を消す処理は要らない。

## 4. 進め方

**いきなり全部作らない。**

| 順 | やること | 確認 |
| --- | --- | --- |
| 1 | **島を1つだけ**設計して描き出す | 画像で形を見る |
| 2 | それを `.mcstructure` にしてゲームに置く | **実際に立って見る** |
| 3 | 良ければ他の島へ。駄目なら 1 に戻る | |
| 4 | 3島そろったら、配置全体を見る | |
| 5 | 拠点の中身（コア・チェスト等）を置く | |

**2 が重要。** 画像で良く見えても、立ってみると違うことがある。
**一番小さい単位で、早く実物を見る。**
