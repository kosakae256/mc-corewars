# 仕様: `genlab` — 文章 → 3D → 20³ ブロック を、ブラウザで試す

> 作成日: 2026-09-21
> 調査: [../research/29-text-to-blocks-feasibility.md](../research/29-text-to-blocks-feasibility.md)
> 発端: [worlds/ai-build-quiz](../../worlds/ai-build-quiz/docs/00-concept.md)
> 実装方針: [../imp.md](../imp.md)（純粋関数の切り出し・コメント厚く・型ガード は Python でも同じ）

## 0. 何のための道具か

**「文章を送ると、その場で 3D が作られ、20×20×20 のブロックになる」が本当にできるかを、Minecraft 抜きで見せる。**

| 見せるもの | |
| --- | --- |
| **任意の単語** を入れる欄 | 日本語でよい。短い句も可 |
| **段ごとの秒数** | ⓪ 翻訳 → ① 画像 → ② 3D → ③ ブロック化。**合計 10 秒に収まるか** |
| **途中経過** | 英語にした語・生成された画像 |
| **ブロック化の様子** | 20³ の格子を **下の層から 1 個ずつ置いていくアニメーション**（ゲームの演出と同じ順） |
| **ゲームに渡す形** | `{ palette, voxels }`（[research/29 2-2](../research/29-text-to-blocks-feasibility.md)）をそのまま表示 |

**ゲーム側（BP スクリプト）は 1 行も書かない。** ここで「秒数」と「見た目」を確かめてから、
[worlds/ai-build-quiz/docs/spec/](../../worlds/ai-build-quiz/docs/spec/) に本番の仕様を書く。

## 1. 構成

```
tools/genlab/
├── README.md              起動のしかた
├── requirements.txt
├── server.py              FastAPI。/ で HTML、/generate で SSE
├── pipeline/
│   ├── translate.py       ⓪ 日本語 → 英語（辞書 → Marian, CPU）。定型は生き物／物で分ける
│   ├── kind.py            生き物か物か（WordNet）
│   ├── level.py           傾きを直す（純粋関数）
│   ├── t2i.py             ① 文章 → 画像（diffusers）
│   ├── i23d.py            ② 画像 → 3D（TripoSR）。**メッシュを作らず 20³ の点を直接問い合わせる**
│   ├── voxel.py           ③ 占有＋色 → palette / voxels（**純粋関数。torch に依存しない**）
│   └── palette.py         ブロックの色表（**固定ルール。AI は使わない**）
├── static/index.html      画面。three.js で 20³ を描き、下から置く
├── shim/torchmcubes/      TripoSR が import する `torchmcubes` の空の代用（2-2）
└── .venv/  TripoSR/  out/ （git 管理外）
```

**ワールド共通の `tools/` に置く。** 3D → ブロックの部分は、このゲーム以外でも使える。

## 2. 段ごとの決め

### 2-0. ⓪ 読み取り — **LLM は使わない**（2026-09-21 変更）

> ### 入力は「単語」にする。だから LLM は要らない
>
> 本人の判断: **出題者に入れてもらうのは文章ではなく単語。**
> 「答え」は入力そのものなので、LLM に答えの単語を出させる必要も無い。
> **Ollama（9b で 6.6 GB）を常駐させると、12 GB に画像＋3D と同居できない**のも理由。

| | |
| --- | --- |
| 入力 | 単語か短い句（日本語）。例: 「犬」「赤い車」 |
| 翻訳 | 画像モデル（CLIP）は日本語を読めないので、**日本語 → 英語だけ**やる。**① JMdict（和英辞書, EDRDG, CC BY-SA）に完全一致すれば辞書**（`build_jmdict.py` → `jmdict_min.json`。単語は辞書が一番正確。Marian は ロケット → Lockett と訳す）。**② 無い句は `Helsinki-NLP/opus-mt-ja-en`（Marian, 約 300 MB）を CPU で**。VRAM 0、0.1 秒 |
| ASCII なら | 翻訳しない（英語で入れた場合はそのまま） |
| **長さの上限** | **Marian に渡す前に切る**（`truncation=True, max_length=512` ＋ 入力を 300 文字まで）。**切らないと長い日本語で `IndexError: index out of range in self` → 500**（2026-09-22 実機。出題モードの詳細が長かった）。画像モデルが読むのは先頭 77 トークンだけなので、切っても絵は変わらない |
| 定型 | **生き物・物・食べ物・植物の 4 種**（`translate.py` の `STYLES`。`style` を指定しなければ `kind.py` の WordNet で生き物／物を選ぶ）。生き物: `a toy figurine of a <x>, full body, …`（全身が安定して出る唯一の言い方）。物: `one <x>, alone, isolated …, clean 3D render`（主語を乗っ取らず丸ごと写す）。**食べ物: `a plastic food replica of a single whole <x>, alone on a white table, …`**、**植物: `a plastic model of a single whole <x>, …`**（物の定型だと果物・野菜・木・花は**接写・山盛り・切り口・風景**になる。5-x「全語テスト」）。1 本にすると 本 → ロボット、剣 → 騎士、猫 → 顔のアップ になる（2026-09-21 比較） |
| 答え | **入力した単語そのもの**。ゲーム側の照合はここでは扱わない |

### 2-0b. 固有名詞の日英辞書（Wikipedia の対訳。2026-09-22）

JMdict は一般名詞の辞書で、キャラ名・地名の多くは載っていない。**日本語版 Wikipedia の記事名 → 英語版の記事名**（langlinks）を一度だけ表にして引く（`build_wikititles.py` → `pipeline/wikititles_ja_en.json`。約 70 万件。CC BY-SA）。リダイレクト（別名・かな表記）も取り込む。

| | |
| --- | --- |
| 引き方 | 空白を除いた題名で完全一致。ひらがなのお題はカタカナにしても引く（じばにゃん → ジバニャン → Jibanyan）。「胡桃 (原神)」は「胡桃」でも引ける（先勝ち） |
| 使う所 | ai-build-quiz の出題モード（[17-modes 3 章](../../worlds/ai-build-quiz/docs/spec/17-modes.md)）: 単語リスト → JMdict → **Wikipedia** → ローマ字、の順 |
| 拾えないもの | 題名が漢字で、かなのリダイレクトが無いもの（ふーたお → 胡桃 (原神)）。英語の詳細で補う |
| なぜ LLM でないか | 実行時は表を引くだけ（0 秒・GPU なし）。小さい LLM は名前を作話し、大きい LLM は GPU を取り合う |

### 2-1. ① 文章 → 画像（diffusers）

| | |
| --- | --- |
| 最初の版 | **SDXL-Turbo**（1〜4 step, fp16, 512×512）。**まず動くことを優先**。入力が単語なので読み取りの弱さは効きにくい |
| 次の版 | Z-Image-Turbo（読み取りが強い）。**モデルは差し替えられる形**にする（`t2i.py` の 1 関数） |
| 常駐 | 起動時に読み込み、以後は推論だけ |

### 2-1b. 生成プロファイル v1 / v2（2026-09-22・本人「今のやつは ver1 として定義。どの状態を使うか指示できるように」）

| プロファイル | 文 → 画像 | なぜ | 状態 |
| --- | --- | --- | --- |
| **v1** | **sd-turbo**（SD 2.1 蒸留、512px、fp16 約 2.5 GB、常駐） | 速い（1 秒）。単語リストはこれで検証してある。**うまく生成できないのも味**（本人） | 予備 |
| **v2** | **SDXL-Turbo**（SDXL 蒸留、512px、fp16 約 7 GB） | 知っている概念が多く、キャラクターの解釈が上がる（本人「あんまりキャラクターを解釈できてない」→ SDXL-Turbo を選択） | **主に使う（既定。本人・2026-09-22「v2 を主に使う」）**。実機で動作（8 秒／回、待機時 VRAM 6.1 GB） |
| **v3** | **Japanese Stable Diffusion XL**（`stabilityai/japanese-stable-diffusion-xl`。SDXL 1.0 を日本語の文字エンコーダで OFT 微調整。fp16 約 6.5 GB、768px、25 step ＋ guidance 7） | **日本語のプロンプトをそのまま読む**（本人・2026-09-22「これ入れて ver3 としよう」）。翻訳・ローマ字が要らない。じばにゃん等を日本語の学習データで知っている可能性 | **使わない**（本人・2026-09-22「v3 はダメそう」）。日本語は読めるがキャラを知らない（ぴかちゅう → 女の子のグリッド）。コードとモデルは残すが、コンパスには出さない |

**v3 の入手**: HF の gated モデル（名前・メール等のフォームに答えると自動承認）。ライセンスは STABILITY AI COMMUNITY LICENSE（非商用・年商 100 万ドル未満は無償。商用は別契約）。手順: ① モデルページで承認 → ② `huggingface-cli login`（トークン）→ ③ `prefetch_v3.py`。
**v3 の落とし穴**: 同梱パイプラインは diffusers 0.2x 向けで、0.39 では `check_inputs` の引数数が合わず 500 になる（2026-09-22 実機）。`t2i.py` の `_patch_jsdxl_check_inputs` で新しい引数並びに差し替えて親の検査に流す。
**v3 の実測（2026-09-22・出題モード 3 問）**: 日本語の文は読めるが **固有名詞のキャラは知らない**（巨人 → 緑の筋肉質の男のフィギュア、胡桃 → 白服の女の子、かーびぃ → 白いアンドロイドの顔 2×2 グリッド）。19 秒／枚。中立の定型だと顔のアップ・グリッドが出るので、negative にグリッド・コラージュ・顔のアップを足し、辞書に無い言葉（＝キャラ名）は生き物の定型にした。**名前で当てたいなら Animagine XL（Danbooru タグ）＋ 日本語別名辞書が要る**（未着手）。
**v3 のプロンプト**: 英語に訳さず **日本語のまま**（`/build?ja=<日本語>`。bridge は単語リストの `ja`、出題モードはお題＋詳細を渡す）。定型も日本語（`translate.py` の `STYLES_JA`）。`ja` が無ければ英語の `text` を使う（JSDXL は英語もある程度読む）。

**VRAM の内訳（RTX 5070・12 GB）**。ホストが同じ PC で Minecraft を動かす（約 2.3 GB）ので、genlab に使えるのは **約 9.5 GB**:

| | v1 | v2（そのまま） | v2（オフロード） |
| --- | --- | --- | --- |
| Minecraft | 2.3 | 2.3 | 2.3 |
| 画像モデル | 2.5 | 7 | 使う瞬間だけ UNet 5.1 ＋ 作業 1（他は CPU RAM） |
| Hunyuan3D-2mini | 3.9 | 3.9 | 画像を作る間は CPU へ退避（0.3 秒 × 2） |
| 合計 | 8.7 | **13.2 → 溢れる**（2026-09-21 に実測: スワップして 2 step に 39 秒） | **約 8.7（画像中）／ 6.2（3D 中）** |

つまり v2 は **「画像モデルは `enable_model_cpu_offload`、3D モデルは画像を作る間だけ CPU へ」の順番運転**で収める。CPU RAM は 31 GB（v1 2.5 ＋ v2 7 ＋ Hunyuan 4 が乗る）。代償は 1 回あたり数秒（PCIe の往復）。**v1 と v2 の両方を GPU に常駐はしない**（v2 を選んだら v1 を CPU へ、戻したら逆）。

| | |
| --- | --- |
| 指定 | `GET /build?profile=v1|v2|v3`（`/generate` も）。無ければ v1。v3 は `ja=<日本語>` も。`text` `detail` `ja` は 4000 文字まで通す（画像モデルは先頭 77 トークンしか読まない。長い文をそのまま活かすなら、CLIP の埋め込みを 77 トークンずつ繋ぐ `sd_embed` 方式が要る——未着手） |
| 切り替え | 最初の v2 呼び出しで読み込む（**モデルは先に `prefetch_v2.py` で落としておく**。約 7 GB。読み込みは 20 秒）。プロファイルが変わった呼び出しで、使わない方を CPU へ |
| `/health` | `profiles: { v1: 読み込み済みか, v2: 同 }` を返す |
| 誰が選ぶか | 運営のコンパス「生成モデル」→ scoreboard `quiz` の `gen`（0 = v1 / 1 = v2）→ bridge が `profile` で渡す（[worlds/ai-build-quiz/docs/spec/13-transport.md](../../worlds/ai-build-quiz/docs/spec/13-transport.md) 3 章・6 章） |
| 単語リスト | v1 の絵で検証したもの。v2 では絵が変わる（味の違い）。v2 用の再検証は別途 |

### 2-2. ② 画像 → 3D（TripoSR）

| | |
| --- | --- |
| モデル | `stabilityai/TripoSR`（MIT） |
| **メッシュを作らない** | TripoSR は triplane NeRF を出す。`renderer.query_triplane(decoder, points, scene_code)` で **任意の点の `density_act` と `color`** が取れる。**欲しいのは 20³ の占有と色だけ**なので、**格子の点を直接問い合わせる**。marching cubes（`torchmcubes`）は要らない |
| なぜ | `torchmcubes` は CUDA 拡張を**コンパイル**する。この PC に `cl.exe` も CUDA toolkit も無い。**そもそも要らないものを入れない** |
| `shim/torchmcubes/` | TripoSR のソースが `import torchmcubes` するので、**空の代用**を置いて import を通す。`marching_cubes()` を呼ぶと例外にする（呼ばないので通らない） |
| 解像度 | 20³ に **上下左右 2 倍のサンプル（40³）** を取り、2×2×2 の多数決で占有を決める。**細い所が消えるのを減らす** |
| 背景 | 画像は白背景で作る。`rembg` で切り抜き、TripoSR の作法どおり灰色（0.5）で埋める |

### 2-3. ③ ブロック化（純粋関数）

| | |
| --- | --- |
| 収め方 | TripoSR の `radius` の箱を 20³ に等分。**一番下の占有層を y=0 に落とす**（接地） |
| 中身 | **柱ごとに最下〜最上の間を詰める**（殻の中身。床までは埋めない——浮いた物に台座が生えるので）。殻のみは切替で残す |
| 色 → ブロック | **使えるのは羊毛・コンクリート・テラコッタだけ**（2026-09-21 決定。各 16 色 ＋ 無着色テラコッタ `hardened_clay` の 49 種。釉薬テラコッタは模様が付くので除外、コンクリートパウダーは別物なので除外）。**色はリソパの実物テクスチャの平均値**を `tools/genlab/palette_from_rp.py` で `bedrock-samples/resource_pack` から取り、`pipeline/palette_data.json` に固定する。目分量で書かない。選ぶのは **RGB の距離が最も近いもの**。**AI は使わない。同じ入力なら同じ出力** |
| **細部を残す** | 20³ に落とすとき、**2×2×2 の多数決（4/8 以上）だとタイヤのような細い部分が消える**（白い車で発生、2026-09-21）。**閾値を下げる（2/8 以上）**か、**細かい格子を 60³ にして 3×3×3 の 5/27 以上**にする。どちらが良いかは実物で決め、結果を 5 章に書く |
| 出力 | `{ "palette": ["air", …], "voxels": "<8000 文字>" }`。`voxels[i]` は `palette` の添字を 1 文字（`0-9A-Za-z`）にしたもの。**添字 = y×400 + z×20 + x**（下の層から） |

### 2-4. 画面

| | |
| --- | --- |
| 入力 | 文章 1 行 ＋「生成」 |
| 進捗 | SSE で段ごとに `{ stage, seconds, ... }` を流す。**段が終わるたびに秒数が埋まる** |
| 3D 表示 | three.js。ブロックを **`palette` の色の立方体**で描く。**下の層から 1 個ずつ置く**（速さ調整つき）。マウスで回せる |

| 保存 | `out/<日時>/` に 画像・`voxels.json`・秒数 を残す（後で見比べる） |

## 5. 実装して分かったこと（2026-09-21）

**結果は [research/29 7 章](../research/29-text-to-blocks-feasibility.md)。** 仕様からずれた点だけここに書く。

| 仕様 | 実際 |
| --- | --- |
| 2-1 画像は SDXL-Turbo | **sd-turbo**。SDXL は fp16 で 7 GB あり、Minecraft と同居すると溢れた |
| 2-1 1〜4 step | **2 step** を既定に。1 step だと指示の効きが甘い |
| 2-0 定型の文 | **「toy figurine, three-quarter front view, eye-level shot, full body, standing on a flat white floor」**（`translate.py` の `STYLES`）。上から見下ろす絵は傾きの元になるので禁止 |
| 2-2 40³ を 1 回 | **2 回**。粗い 32³ で外接箱と傾きを測り、40³ は**水平に直した座標で**問い合わせる（`i23d.py`） |
| — | **傾き補正**を足した（`level.py`）。「床に接する柱が最大になる角度」。接地が 1.5 倍＋2 柱以上増えるときだけ回す |
| — | **一番大きい塊だけ残す**を足した（画像のマスクと立体の占有）。別の物・浮きかすを捨てる |
| 2-3 床から詰める | **柱ごとに最下〜最上の間だけ詰める**。床まで埋めると浮いた物に台座が生える |
| 背景抜き | rembg **u2netp**（4.7 MB・0.13 秒）。u2net（176 MB・0.27 秒）は要らなかった |
| 翻訳 | Marian opus-mt だけでは**カタカナ語に弱い（ロケット → Lockett）** → 辞書を先に引く形にした（5-1） |

補助の道具（全部 `tools/genlab/`）:

| | |
| --- | --- |
| `bench.py 犬 --repeat 3` | 段ごとの秒数と VRAM |
| `batch.py 犬 車 …` | 複数語の画像と 20³ を 1 枚に |
| `compare.py cat dog … --seed 7` | 様式 × 閾値 × step を同じ seed で比較 |

### 5-1. 2 回目の直し（2026-09-21・本人の指摘 3 件）

| 指摘 | 直し |
| --- | --- |
| **ブロックは羊毛・コンクリート・テラコッタだけ。色はリソパから** | `palette_from_rp.py` が `bedrock-samples/resource_pack` の実物テクスチャの平均 RGB を `palette_data.json` に固定（49 種）。手書きの表は廃止 |
| **タイヤが潰れる** | 2×2×2 の多数決を **4/8 → 2/8** に（`voxel.MIN_SUBCELLS`）。白い車で黒いタイヤが残るようになった |
| **色は影を無視** | `voxel.unshade()`。同じ色味の点を集まりにまとめ、**その集まりの上位 90% の明るさに揃える**。本当に暗い色（max < 60）は黒として触らない。白い車が灰・紫のブロックにならなくなった |
| 「本」が「本のフィギュア」になる | 定型を生き物／物で分けた（2-0）。判定は WordNet |
| ロケット → Lockett | 辞書を先に引く（2-0） |

### 5-2. 大きさを変えたら（2026-09-21・本人の問い「80×80 にしたら？」）

`SIZE` を可変にして同じ語を流した（象・赤い車、seed 固定、Minecraft を開いたまま）。

| | 20³ | 40³ | 80³ |
| --- | --- | --- | --- |
| 生成の合計 | 0.7 s | 0.8 s | **1.5〜1.9 s** |
| ブロック数（象／車） | 1,344 / 399 | 9,896 / 2,736 | 75,327 / 19,981 |
| 渡す文字数 | 8,000 | 64,000 | 512,000 |
| 見た目 | 動物と分かる | **象と分かる**（鼻・耳・脚） | 40³ と情報は同じ。表面が滑らかになるだけ |

- **速さは問題にならない。** 80³ でも 2 秒未満（ブロック化を numpy にした。Python のループだと 80³ で数十秒）
- **形の情報は 40³ で頭打ち。** 元の 3D（TripoSR）の細かさに上限がある
- 80 ブロックは 25 階建て相当。**置く時間（1 tick 1,300 個の全力で 3 秒）と見渡す距離がゲーム側の制約**になる
- **40³ が現実的な上限**。20 か 40 かは置く演出と見る距離で決める（企画側）

### 5-3. 3D を Hunyuan3D-2mini turbo に替える（2026-09-21・本人の「もっと精度上げれない？」→ 比較して決定）

**TripoSR（1 枚から復元）→ Hunyuan3D-2mini turbo（学習した 3D の知識で形を生成）。** 同じ画像で比べた（`hy_test2.py`、`out/hy-test2.png`）:
家は屋根・煙突・壁が両側から分かり、犬はどちらから見ても犬。TripoSR は前だけ・裏は崩れる。

| | TripoSR | **Hunyuan3D-2mini turbo** |
| --- | --- | --- |
| 3D の段 | 0.3 秒 | **2.5 秒**（5 step） |
| VRAM（sd-turbo 込み・この処理） | 約 4 GB | **約 6.2 GB**（TripoSR は外す。Minecraft 込み 8.5〜9 GB） |

#### 形の取り方（`i23d_hy.py`）

| | |
| --- | --- |
| 入力 | rembg で抜いた RGBA（一番大きい塊だけ）。Hunyuan3D 側が 512² に寄せ直す |
| 潜在 → 格子 | `output_type="latent"` で潜在を取り、VAE の **volume decoder に n³ の格子を直接出させる**（`bounds` に外接箱を渡せる）。メッシュは作らない |
| 外接箱 | 粗く 32³ を出して占有の箱を取り、**その箱の中だけ**を n³ で出す（TripoSR 版と同じ考え） |
| 向き | Hunyuan3D の出力は **y が上**で、そのまま使える（比較で確認）。傾き補正は残すが、接地が明らかに増えるときしか回らない |
| 中の詰め | **占有そのもの**（生成モデルは中身まで出す）。`fill_between` は**切る**（下の「溶ける」） |

#### 色の付け方（画像の投影）

Hunyuan3D は形だけなので、**生成画像の色を平行投影で貼る**。

1. 画像の alpha の外接箱と、占有の外接箱（カメラ方向から見た 2 軸）を対応付ける
2. **カメラがどの軸か**は、占有の影絵と alpha の重なり（IoU）が最大の向き（±x / ±z、鏡像あり）を毎回選ぶ。数 ms
3. 占有セルすべてに、その位置の画素の色を付ける（裏側も同じ色。見えない側の色は分からないので割り切る）
4. その後は今までどおり `unshade` → 羊毛・コンクリート・テラコッタへ

#### タイヤが黒くない（同日・本人の指摘）

| --- | --- |
